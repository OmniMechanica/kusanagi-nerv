## Objective

Connect the durable control plane to Ray without losing consistency across restarts.

## Implementation steps

- Implement the [executor contract](../../02-architecture/components.md#contract-between-control-and-execution) using Ray Jobs on a separately running local cluster; keep Ray Core examples from MLP-006 as learning exercises.
- Persist a deterministic `submission_id` for each job/attempt before calling Ray; use it for submit/status/cancel, including when the submit response is lost. Record the target cluster.
- Reconcile unknown or stale attempts after API/controller restart and process actual results.
- Implement a deterministic dummy workload and state transitions `QUEUED -> RUNNING -> SUCCEEDED`.
- Write one end-to-end API → controller → Ray → Postgres test.

## Acceptance criteria

- [x] HTTP returns before Ray work ends; Ray processes execute separately.
- [x] Job state remains available through controller restart.
- [x] Repeated reconciliation does not launch uncontrolled duplicate work.
- [x] Crash after submit/before acknowledgment, cancel before a running observation, unknown lookup, and completion between polls have deterministic failure-injection coverage.
- [x] Duplicate submission of the same identity is reconciled; a new attempt is created only after a confirmed failure under the retry policy.
- [x] Integration test passes with a real local Ray runtime.
