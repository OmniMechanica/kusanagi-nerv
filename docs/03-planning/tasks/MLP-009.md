# MLP-009 — Ray Train multi-worker training and DDP concepts

**Project:** KUSANAGI NERV  
**Priority:** P0  
**Schedule:** Day 09  
**Learning/build timebox:** 3–5 h (estimate, not a deadline)  
**Status:** Planned  
**Dependencies:** [MLP-006](MLP-006.md), [MLP-008](MLP-008.md)

## Objective

Run distributed training and explain multi-worker synchronization semantics.

## Implementation steps

- Wrap the tiny PyTorch model in a Ray Train workflow.
- Set the MVP runtime retry policy explicitly as described in [retry ownership](../../02-architecture/reliability.md#retry-ownership); internal worker recovery is disabled for the later controller-owned recovery experiment.
- Run at least two CPU workers and verify process/rank behavior.
- Explain `torchrun`, world size, DDP gradient sync, FSDP model-state sharding and where NCCL is relevant on GPUs.
- Parameterize CPU vs GPU allocation explicitly without automatically falling back for GPU-required jobs.
- Produce a typed result usable by the execution adapter; integration with the durable controller is required in MLP-010, after MLP-007.

## Acceptance criteria

- [ ] Multi-worker CPU training executes with recorded worker count.
- [ ] Model and metrics are produced; repeated run uses comparable configuration.
- [ ] You can whiteboard DDP vs FSDP and describe GPU-specific validation not yet performed.
- [ ] The execution result is consumable by the job controller.
- [ ] An attempt-scoped training-start signal distinguishes driver startup from actual training; a driver waiting for GPU workers does not prematurely make the job `RUNNING`.

## Required evidence

TESTED-CPU for distributed run; DESIGN-ONLY for GPU-specific behavior until real hardware is used.

## What to study in parallel

Official Ray Train, PyTorch distributed overview and DDP/FSDP docs.

## Interview drill

Why DDP instead of training one giant Python process? How does gradient synchronization affect throughput?
