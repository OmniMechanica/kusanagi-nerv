## Objective

Run scheduling in a separate process and claim queued work without duplicate owners.

## Implementation steps

- Create a controller service/entrypoint independent from the FastAPI process.
- Implement safe DB claim/lease using a transaction (`FOR UPDATE SKIP LOCKED` or equivalent).
- Record attempt IDs, stable submission ID and intent before dispatch, lease owner/epoch/expiration and heartbeat or claim timestamps.
- Create a temporary local executor adapter to simulate work while preserving the later Ray interface.
- Test two simultaneous controllers competing for the same pending job.

## Acceptance criteria

- [x] Two controllers never hold the authoritative active claim for one attempt at the same time.
- [x] Controller crash/lease expiry allows another process to reconcile and continue.
- [x] API acknowledgement is independent of controller availability.
- [x] Attempt identifiers are persisted and traceable.
- [x] A stale lease holder cannot commit results; fake-executor tests distinguish unknown submit outcomes from confirmed failures without creating another attempt.

## Implemented boundaries

The controller uses PostgreSQL claims and leases, short transactions and bounded
executor calls. `0002_attempt_leases` persists submission intent before dispatch;
takeover keeps the attempt/submission identity and increments the lease epoch.
Guarded observations atomically update the attempt and job; version-only writes
cannot modify a job after its first dispatch intent.

The durable local executor is explicitly `SIMULATED`: elapsed DB time, no model
training/artifacts or resource allocation. It admits CPU requests only. Each
controller owns at most one active attempt. Actual Ray semantics remain MLP-007;
HTTP idempotency, retries/backoff and cancellation remain MLP-005. Confirmed failure
is terminal in this increment even when the request includes a retry budget.
