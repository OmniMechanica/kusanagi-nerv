## Objective

Enforce correct admission and recovery behavior under duplicate requests and competing outcomes.

## Implementation steps

- Implement tenant-scoped `Idempotency-Key` with payload digest and database uniqueness.
- Define retryable vs non-retryable errors; the controller owns at most `1 + max_retries` attempts, with persisted exponential backoff/jitter. Unknown remote outcomes stay on the same attempt until reconciled.
- Expose `POST /v1/jobs/{id}/cancel` as cancellation **request**, not immediate success guarantee.
- Implement cancellation race handling and state version/compare-and-swap updates, including pending or in-flight dispatch. After submission intent, use `CANCELLING` until safe termination is confirmed; cancellation suppresses retries.
- Write deterministic concurrent tests with barriers/events (avoid flaky sleeps).

## Acceptance criteria

- [x] Same key and payload returns same job ID; same key with different payload returns 409.
- [x] Retries preserve job identity and create explicit attempt records.
- [x] Terminal states cannot be retried accidentally; cancelled work does not report success without observation.
- [x] Concurrent submit/cancel tests pass.
- [x] Already-terminal cancellation returns the existing state without a transition; unknown submit outcomes do not consume retry budget or falsely report cancellation.

## Implementation boundaries

Idempotency is optional and tenant-scoped, backed by PostgreSQL uniqueness; requests
without a key remain independent. Retry deadlines and failure classification are
durable. Cancellation intent suppresses retries, while lease/attempt guards protect
observations. The simulator retains cancellation records that reject delayed submits.
No retention/expiry policy deletes keys or cancellation records yet.

Execution and injected worker failures are `SIMULATED`; database concurrency and
process-restart evidence are `TESTED-CPU`. Ray's stop/reconciliation semantics and
checkpoint recovery require later adapter/training work. The fixed tenant remains
test-only. Gate A's technical scenarios are covered, but learner checkpoints remain
open; this ticket and the gate are not marked Done solely from test output.
