## Objective

Implement reliable, explicit job-state transitions before introducing infrastructure.

## Implementation steps

- Use `enum.StrEnum` to represent CREATED, QUEUED, RUNNING, RETRYING, CANCELLING, SUCCEEDED, FAILED and CANCELLED, with lowercase string values for the API.
- Implement `can_transition(current, new)` as a pure, typed function; keep the allowed transition map immutable.
- Implement pure `transition(current, new) -> JobStatus`; return the new state on valid edges and raise `InvalidJobTransition` with current/requested states on invalid edges.
- If `challenges/job_lifecycle_cases.py` exists, compare it with the current specification before reusing it. Cover all 64 state pairs: 18 allowed and 46 forbidden. Expected outcomes must come from the specification, not the implementation's transition map.
- Write a short design note explaining attempts, retry cycles and terminal-state invariants.

## Acceptance criteria

- [x] Every transition in `docs/01-product/job-lifecycle.md` is allowed and every omitted transition is forbidden.
- [x] Terminal states cannot be restarted or self-transitioned.
- [x] Deterministic scenarios explain `CANCELLING -> SUCCEEDED`, failure before a running observation, and `QUEUED -> SUCCEEDED` when polling misses a short run.
- [ ] Explain why `QUEUED -> CANCELLED` needs a contextual no-dispatch guard later; graph tests alone do not prove remote cancellation or concurrency safety.
- [x] Tests and Ruff pass.
- [ ] You can explain why retry is a state and not a new logical job.

The [design notes](../../01-product/job-lifecycle.md#mlp-001-implementation-notes) cover attempts, retry cycles, terminal states and contextual guards. The unchecked items require the learner's explanation, not additional MLP-001 infrastructure.
