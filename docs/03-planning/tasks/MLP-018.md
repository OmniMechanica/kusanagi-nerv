# MLP-018 — Prometheus metrics, autoscaling signals and cost model

**Project:** KUSANAGI NERV  
**Priority:** P1  
**Schedule:** Day 18  
**Learning/build timebox:** 3–4 h (estimate, not a deadline)  
**Status:** Planned  
**Dependencies:** [MLP-011](MLP-011.md), [MLP-016](MLP-016.md)

## Objective

Expose enough evidence to reason about reliability, queue wait and GPU allocation cost.

## Implementation steps

- Instrument request latency, status counts, queue depth/age, retries, failures and training duration.
- Add simple inference load testing and inspect Ray Serve autoscaling configuration/behavior.
- Sketch KubeRay/cluster node autoscaling relation and queue demand signal.
- Implement an explicit allocated GPU-hours cost estimate with configurable price.
- Keep job ID out of high-cardinality metric labels.

## Acceptance criteria

- [ ] Metrics endpoint reports bounded-cardinality signals.
- [ ] Queue wait is distinct from training run time.
- [ ] GPU-hour figures are labelled estimated and use allocated capacity, not GPU utilization.
- [ ] One load test and basic metric inspection are documented.

## Required evidence

TESTED-CPU metrics/load; DESIGN-ONLY for simulated GPU cost if no hardware.

## What to study in parallel

ML Production monitoring lessons, Ray Serve autoscaling guide, Prometheus docs.

## Interview drill

What SLO would you assign to batch training versus low-latency serving? Why not put `job_id` in Prometheus labels?
