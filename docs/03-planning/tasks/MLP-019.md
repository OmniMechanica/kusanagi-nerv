# MLP-019 — Architecture decisions, Flyte comparison, CI and security

**Project:** KUSANAGI NERV  
**Priority:** P1  
**Schedule:** Day 19

**Status:** Planned  
**Dependencies:** [MLP-015](MLP-015.md), [MLP-017](MLP-017.md), [MLP-018](MLP-018.md)

## Objective

Make the design reviewable and show production-minded tradeoffs.

## Implementation steps

- Write/validate ADRs for Postgres queue, Ray vs Flyte, checkpoints and failure semantics.
- Create a compact comparison of Flyte DAG orchestration vs Ray execution with use cases.
- Extend the lint/unit CI established during bootstrap with DB/API integration checks where feasible; preserve the fast basic checks.
- Review the P1 follow-up from MLP-001/002: add a mypy or Pyright baseline and CI check. Static analysis is deferred and does not block the earlier API increment.
- Run a brief security review: tenant auth, artifact access, secrets, untrusted inputs, image supply chain.
- Document non-goals, open risks and capacity assumptions.

## Acceptance criteria

- [ ] All architecture decisions have context, alternatives, consequences.
- [ ] Expanded CI reproducibly exercises DB/API integration or documents unavailable external dependencies; existing lint/unit checks remain green.
- [ ] Security/tenancy risks and mitigations are explicitly recorded.
- [ ] Can explain when Ray and Flyte complement one another.

## Required evidence

TESTED-CPU for CI; DESIGN-ONLY for architecture/security claims without live enforcement.

## What to study in parallel

Flyte docs, role skill matrix, ADRs and project risk register.

## Interview drill

What would change first at 10x scale? When would you add a broker or managed orchestrator?
