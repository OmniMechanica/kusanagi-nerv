# MLP-016 — GPU scheduling, capacity and topology design

**Project:** KUSANAGI NERV  
**Priority:** P0  
**Schedule:** Day 16  
**Learning/build timebox:** 2–4 h (estimate, not a deadline)  
**Status:** Planned  
**Dependencies:** [MLP-015](MLP-015.md)

## Objective

Explain how GPU capacity is exposed, requested, allocated, isolated and observed.

## Implementation steps

- Describe NVIDIA drivers, container runtime, GPU Operator and device plugin requirements.
- Define `nvidia.com/gpu` resource requests in example Pod/Ray worker manifests.
- Compare dedicated GPUs, MIG and time slicing, including isolation and memory tradeoffs.
- Design behavior for no GPU capacity, queue wait, fairness, allocation-cost estimates and autoscaling layers.
- Optional: execute one real GPU job only when suitable hardware is available.

## Acceptance criteria

- [ ] GPU manifest has correct extended resource intent and prerequisites.
- [ ] Architecture describes pending capacity, quota and scheduling failure reasons.
- [ ] MIG/time-slicing/DDP topology tradeoffs are defendable.
- [ ] No real GPU performance claim without hardware proof.

## Required evidence

DESIGN-ONLY by default; TESTED-GPU only if actual run records GPU/device and metrics.

## What to study in parallel

Kubernetes GPU scheduling, NVIDIA GPU Operator/MIG/DCGM, PyTorch distributed docs.

## Interview drill

How would you admit 500 requests on 32 GPUs? Distinguish allocation from utilization and three scaling loops.
