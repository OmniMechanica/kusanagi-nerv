# MLP-015 — KubeRay and Kubernetes deployment artifacts

**Project:** KUSANAGI NERV  
**Priority:** P0  
**Schedule:** Day 15  
**Learning/build timebox:** 3–4 h (estimate, not a deadline)  
**Status:** Planned  
**Dependencies:** [MLP-013](MLP-013.md)

## Objective

Map the platform execution plane to Kubernetes resources without confusing runtime and cluster responsibilities.

## Implementation steps

- Prepare CPU-first RayCluster/RayJob/RayService manifests or Helm overlays with explicit resources.
- Define service accounts, image strategy, storage and config mounts at design level.
- Validate manifests and, if practical, demonstrate CPU Ray on kind or an existing local K8s cluster.
- Document distinctions between Ray worker replicas, Kubernetes Pods and cluster node autoscaling.
- Record tested vs design-only components.

## Acceptance criteria

- [ ] Manifests/configs pass validation and document prerequisites.
- [ ] CPU workload executes on K8s if environment allows, otherwise blockers and architecture-only scope are explicit.
- [ ] Pod health, Ray job status and deployment topology are inspectable.
- [ ] KubeRay failure domains are explained.

## Required evidence

TESTED-CPU or DESIGN-ONLY, explicitly tagged; manifest validation output.

## What to study in parallel

KubeRay docs and Kubernetes workloads/controller docs.

## Interview drill

Which layer owns pod placement, runtime tasks and head-node availability? How does KubeRay fit in?

## Definition of Done

Pass applicable checks in [Definition of Done](../../06-engineering/definition-of-done.md); log result and evidence in [progress](../progress.md). Do not call design-only work a successful hardware run.
