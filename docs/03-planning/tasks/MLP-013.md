## Objective

Prove the core platform works as a coherent, reproducible system.

## Implementation steps

- Create scripted startup for FastAPI, controller, PostgreSQL, MinIO and Ray services.
- Submit training job via API; observe queued/running, save checkpoint and finish model artifact.
- Inject a worker failure on a training attempt and verify checkpoint resume.
- Read `result_model_id` from the successful job, call the public deploy API, poll model readiness and issue prediction. The test must work without MLP-012's SDK or manual Ray deployment commands.
- Automate happy path and failure path as reliable integration/E2E tests.

## Acceptance criteria

- [ ] `submit -> train -> checkpoint -> recover -> serve -> predict` completes with recorded result.
- [ ] Restarting API does not erase job state.
- [ ] HTTP requests do not block until training completion.
- [ ] Reproducible runbook and execution proof are saved.

## Required evidence

TESTED-CPU: single-command or documented E2E run with logs/artifact/checkpoint URI.

## What to study in parallel

Review project architecture and Ray Train/Serve official docs.

## Interview drill

Explain each component boundary in under five minutes; identify the three weakest production assumptions.

Pass applicable checks in [Definition of Done](../../06-engineering/definition-of-done.md); log result and evidence in [progress](../progress.md). Do not call design-only work a successful hardware run.
